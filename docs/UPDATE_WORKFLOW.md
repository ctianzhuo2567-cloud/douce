# 预览、同步与更新方案

## 电脑预览分三层

1. `预览豆册界面.bat`：最快，查看视觉与基本交互，不需要安装开发工具。
2. Android Studio Compose Preview：逐个查看静态安卓页面，适合调布局。
3. 安卓模拟器或实体手机：最终验收，能验证图片权限、性能、手势、存储和安装升级。

浏览器预览不是另一个产品，也不保存真实资料；正式功能只在 Android App 中实现。

## 推荐的代码同步方式

项目初始化为 Git 仓库后，每次完成一个可用功能就形成一次本地提交。需要跨电脑或防止硬盘损坏时，再连接一个私有 GitHub 仓库。

建议分支：

- `main`：始终保留可安装版本。
- `feature/...`：开发中的单项功能，例如 `feature/legend-ocr`。

测试通过后才把功能合并到 `main`。测试图片和用户图纸不上传公共仓库；签名密钥绝不能提交到 GitHub。

## APK 覆盖更新必须满足

- `applicationId` 始终为 `com.pindou.patternbook`。
- 始终使用同一个正式签名密钥。
- 新版本的 `versionCode` 必须大于手机里已安装版本。
- 数据结构升级必须写迁移逻辑，不能靠清空数据解决。

只要这四点保持一致，新 APK 可以直接覆盖安装，本地图纸信息不会因为升级被清空。正式签名密钥一旦丢失，旧安装通常无法继续覆盖升级，因此至少离线备份两份，并分别保存密码。

## 开发与发布节奏

```text
修改功能
  ↓
电脑浏览器看交互方向
  ↓
安卓模拟器 / 真机验收
  ↓
自动测试与备份恢复测试
  ↓
递增版本号并生成签名 APK
  ↓
手机覆盖安装
```

私人使用阶段不建议先做应用商店发布。更轻的方式是生成签名 APK，通过 USB、局域网或私有 GitHub Release 传到手机安装。等功能稳定、确实需要多人使用时，再考虑应用商店和自动更新。

## 后续可以自动化

连接私有 GitHub 后，可以增加自动构建：每次推送先运行测试；打版本标签时自动生成 APK。正式签名建议使用 GitHub 加密变量，仓库中只保留构建配置，不保留密钥文件和明文密码。
